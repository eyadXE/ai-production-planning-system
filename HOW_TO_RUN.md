# How to run this demo (Windows)

This is a full-stack app: a Python/FastAPI backend and a Next.js frontend,
talking over a same-origin API proxy.

## 0. One-time setup

```powershell
# from the repo root
python -m venv .venv
.venv\Scripts\pip install -e . pytest python-dotenv python-multipart email-validator
copy .env.example .env
```

Open `.env` and leave the LLM keys blank if you don't have any — the app
works fully offline via its deterministic rules engine and a guided-interview
fallback for the chat. `OUSUS_JWT_SECRET` is already filled with a random
local value; change it if you like.

### About the demo data

The original business data (`OUSUS/Ousus_data/`: catalog pricing, the rate
handbook, 27 sample client job specs, and the golden answer key) was never
pushed to GitHub — it's excluded by `.gitignore` and only ever existed on
the machine it was built on. Everything in that folder right now is a
**synthetic placeholder** generated by `scripts/generate_mock_data.py` so the
platform has something real to seed, estimate, and schedule against. Numbers
(prices, stock levels, account names) are made up — the 24-product catalog
itself (`src/finalproject/db/products_data.py`) is real and was already in
the repo.

If you ever want to regenerate that placeholder dataset (e.g. dates have
drifted — see note below):

```powershell
.venv\Scripts\python scripts\generate_mock_data.py
```

**Note on dates:** `capacity.json` is generated relative to "today" so the
demo's fully-booked week block always sits in the near future. The two
hardcoded week labels in `tests/test_tracking.py::test_daily_summary_matches_golden_expectations`
(`fully_booked_weeks` / `first_meaningful_free_week`) are tied to whatever
date the data was generated on. If you regenerate the data on a different
day and that one test fails, just read the new labels out of the JSON
response and update those two literals — everything else self-adjusts.

## 1. Seed the database

```powershell
.venv\Scripts\python -m finalproject.db.seed --fresh
```

## 2. Run the backend

```powershell
.venv\Scripts\uvicorn finalproject.api.main:app --port 8000
```

Leave this running. API docs: http://localhost:8000/docs

## 3. Run the frontend (separate terminal)

```powershell
cd frontend
npm install
npm run build
npm run start
```

Open http://localhost:3100 — this is what you record. The frontend proxies
`/api/*` to the backend at `http://localhost:8000` (same-origin, no CORS
issues). For local dev with hot reload instead of a production build, use
`npm run dev` instead of `build` + `start`.

## What was fixed to get here

- `OUSUS/Ousus_data/` (catalog pricing handbook, 27 job specs, golden answer
  key) didn't exist in the clone — synthetic placeholder data was generated
  (see above) and 4 tests with dates/text hardcoded against the *original*
  data were updated to match (2 stale-date fixtures in `test_llm.py` now use
  `date.today()`, one wrapped clause sentence, one date-anchored capacity
  assertion in `test_tracking.py`).
- `frontend/lib/` (the `api.js`/`cart.js` modules every page imports, plus
  `utils.ts` for the shadcn `cn()` helper) was **silently gitignored** —
  the repo's `.gitignore` had a bare `lib/` rule meant for Python's
  packaging build output, which also matched `frontend/lib/` and kept it out
  of every commit. Fixed to `/lib/` (anchored to repo root) and rebuilt the
  three missing files from how every page in `app/` and `components/`
  already calls them. This was the actual build-breaking bug — without it
  `npm run build` fails outright.
- The "known unsolved bugs" listed in `OUSUS/README_WORKFLOWS.md` (manager
  approval not updating release_status, chat 500s under LLM failure) are
  already fixed in the current code — that doc is stale from an earlier
  session; left as-is rather than rewritten.

## Known limitation

Email notifications need a Gmail app password in `.env`
(`OUSUS_SMTP_PASS`) to actually send; without it, they're written to
`data/email_outbox.log` instead. Fine for a recording — just mention it if
someone asks why no email arrives.
